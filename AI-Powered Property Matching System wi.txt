# AI-Powered Property Matching System with OpenAI

## Overview
This document outlines the requirements for building an AI-powered matching system that uses OpenAI to intelligently connect customer property requests with relevant properties from our inventory. The system leverages OpenAI's language understanding capabilities to parse natural language requests, extract structured data, and perform semantic matching between customer needs and available properties.

---

## Business Requirements

### Core Functionality
1. **AI-Powered Matching**: Use OpenAI to understand customer intent and match with suitable properties
2. **Natural Language Processing**: Parse unstructured text from WhatsApp and web forms
3. **Multi-Source Support**: Handle requests from both web forms and WhatsApp AI agent
4. **Real-Time Updates**: Trigger matching whenever new requests or properties are added
5. **Intelligent Scoring**: Use AI to rank matches by relevance and compatibility
6. **API Endpoints**: Provide RESTful APIs for the frontend matching page

---

## OpenAI Integration Strategy

### Use Cases for OpenAI

#### 1. **Natural Language Understanding**
- Parse unstructured text from `notes` field in web forms
- Extract intent and requirements from WhatsApp `message` field
- Understand vague requests like "family home near good schools" or "investment property in growing area"

#### 2. **Semantic Matching**
- Match customer requirements with property descriptions semantically
- Understand synonyms and related terms (e.g., "villa" = "standalone house", "spacious" = "large area")
- Consider context and implicit requirements

#### 3. **Enhanced Scoring**
- Use AI to evaluate match quality beyond simple criteria matching
- Consider factors like lifestyle fit, investment potential, and customer preferences
- Generate explanation for why properties match

#### 4. **Data Enrichment**
- Extract structured data from unstructured WhatsApp messages
- Normalize location names and property types across languages
- Fill in missing criteria based on context

### OpenAI API Implementation

#### Request Processing Flow
1. **Receive customer request** (from either table)
2. **Prepare OpenAI prompt** with:
   - Customer requirements (structured + unstructured text)
   - Available property criteria to match against
   - Matching instructions and scoring guidelines
3. **Call OpenAI API** to:
   - Extract/clarify requirements
   - Generate search criteria
   - Suggest matching strategy
4. **Execute database query** based on AI-enhanced criteria
5. **Score and rank results** using AI evaluation
6. **Return matches** with AI-generated explanations

#### OpenAI Prompt Structure
The system should construct prompts that include:
- Customer request details (all relevant fields)
- Unstructured text (notes, messages)
- Available property inventory summary
- Matching criteria and priorities
- Output format requirements (JSON with scores and explanations)

## Matching Logic Requirements

### Hybrid Approach: Database + AI

#### Phase 1: Database Pre-filtering (Fast)
Use traditional SQL queries to narrow down candidates based on hard criteria:
1. **Location** - Region, city, district matching
2. **Budget Range** - Price within min/max budget
3. **Property Type** - Exact or category match
4. **Size Range** - Area within specified range
5. **Basic Features** - Bedrooms, bathrooms count

#### Phase 2: AI Scoring & Ranking (Intelligent)
Send pre-filtered properties to OpenAI for intelligent scoring:
1. **Semantic Matching** - Compare descriptions with customer intent
2. **Contextual Fit** - Evaluate lifestyle and goal alignment
3. **Priority Weighting** - Adjust scores based on customer urgency and seriousness
4. **Explanation Generation** - Create human-readable match reasons

### Scoring System
- **Database Match Score** (0-50 points): Based on hard criteria matches
- **AI Semantic Score** (0-50 points): Based on OpenAI evaluation
- **Total Score** (0-100 points): Combined score for final ranking
- **Minimum Threshold**: 60 points for viable matches

## Required API Endpoints for /matching Page

### 1. **GET /api/matching/requests**
**Purpose**: Get all customer requests with their match counts

**Query Parameters**:
- `source` (optional): Filter by source (`web`, `whatsapp`, or `all`) - default: `all`
- `status` (optional): Filter by status (`active`, `read`, `unread`) - default: `active`
- `page` (optional): Page number for pagination - default: `1`
- `per_page` (optional): Items per page - default: `20`
- `sort_by` (optional): Sort field (`created_at`, `match_count`, `urgency`) - default: `created_at`
- `sort_order` (optional): Sort direction (`asc`, `desc`) - default: `desc`

**Response**:

  "data": {
    "requests": [

## Automation Requirements

### Event 1: New Customer Request Added
**Trigger**: New row in `users_property_requests` or `api_customer_inquiry`

**Automated Actions**:
1. **Extract & Enrich Data** (OpenAI)
   - Parse unstructured text from notes/message
   - Extract implicit requirements
   - Normalize and structure data

2. **Find Matches** (Database + OpenAI)
   - Pre-filter properties using database queries
   - Score matches using OpenAI
   - Store matches with scores and explanations

### Event 2: New Property Added
**Trigger**: New row in `user_properties`

**Automated Actions**:
1. **Generate Property Summary** (OpenAI)
   - Create semantic description from property data
   - Extract key selling points

2. **Find Matching Requests** (Database + OpenAI)
   - Query active requests that might match
   - Score compatibility using OpenAI
   - Store matches


### Event 3: Property Updated
**Trigger**: Key fields updated in property tables

**Automated Actions**:
1. **Re-evaluate Matches**
   - Update existing match scores
   - Generate new matches if criteria changed
   - Archive outdated matches

### API Usage Guidelines
- **Model Selection**: Use GPT-4 Turbo for best matching quality
- **Temperature**: Keep low (0.3) for consistent, factual responses
- **Token Management**: Optimize prompts to stay within limits
- **Error Handling**: Implement fallback to database-only matching if API fails
- **Rate Limiting**: Implement queuing for bulk operations
- **Cost Monitoring**: Track API usage and costs per match

### Prompt Engineering Best Practices
- Use structured JSON output format
- Include clear scoring criteria in prompts
- Provide examples of good matches
- Request explanations for transparency
- Handle multiple languages (Arabic/English)

## Technical Considerations

### Performance Optimization
- **Caching**: Cache OpenAI responses for similar requests
- **Batch Processing**: Group multiple properties for single API call when possible
- **Database Indexing**: Index all matching criteria fields
- **Queue System**: Use Laravel queues for async matching operations
- **Fallback Strategy**: Database-only matching if OpenAI API is slow/unavailable

### Data Integrity
- Validate all data before sending to OpenAI
- Sanitize user input to prevent prompt injection
- Handle missing/null values gracefully
- Normalize units (currency, area measurements)
- Validate OpenAI responses before storing

### Security
- Secure OpenAI API key in environment variables
- Sanitize customer data before API calls
- Implement rate limiting on matching endpoints
- Log all API calls for audit trail
- Protect customer PII in logs

### Monitoring & Logging
- Track OpenAI API response times
- Monitor match quality metrics
- Log failed API calls with fallback triggers
- Track cost per match
- Monitor user interactions with matches
